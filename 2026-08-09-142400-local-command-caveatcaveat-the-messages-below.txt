● All 10 pass — including the critical rowcount-abort rollback proof.

  ★ Insight ─────────────────────────────────────
  - test_guard_rolls_back_child_inserts is the linchpin test: a zero-row UPDATE
  is a successful SQL no-op, so without the explicit rowcount == 0 → raise, the
  Category insert in the same transaction would silently commit against a
  superseded run. The raise forces the whole transaction.atomic() block to roll
  back.

  single atomic statement — no read-modify-write race between overlapping
  refresh and reaper bumps.

● ★ Insight ─────────────────────────────────────
  - The fan-in's dedup plan is computed entirely in memory before the REPORT
  network call, then applied inside one short fenced transaction — honoring the
  hard rule "never hold a SQLite writer lock across an LLM call" (§5.3). Holding
  it would block every poll and every sibling category write.
  - Both the finalize and reaper terminal writes use
  filter(status="blue").update(...) — a compare-and-set. Whichever of the two
  runs first wins; the loser's updated == 0 raises SupersededGeneration and
  rolls back. That's how exactly one terminal writer is guaranteed.

● Diagnosis complete and fixed.

  Why Google had no blogs

  It wasn't a bug in exclusion or the curator — both worked correctly. The
  QUERY_PLANNER was the culprit. For Google's blog_posts category it generated
  queries like:

  "latest Google blog posts", "Google AI blog articles", "Google Cloud blog
  updates" …

  Every one of those searches for Google's own blogs, so Tavily returned
  blog.google, opensource.googleblog.com, research.google,
  mapsplatform.google.com, etc. The curator then correctly rejected all of them
  as company_channel — because that category means third-party blog posts (§2).
  Result: 0 accepted → yellow.

  The planner prompt only passed the bare category key (Category: blog_posts)
  and never said we want independent, third-party coverage about the company
  rather than the company's own content. (Apple got 9 blogs because the
  third-party Apple-blog ecosystem — 9to5Mac and friends — is large enough that
  even naive queries surfaced some; Google's own blogs dominate its blog
  searches.)

  The fix

  1. Third-party-targeted planner — the QUERY_PLANNER prompt now states it's
  finding independent, third-party content about the company, carries a
  per-category intent (e.g. blog_posts → "blog posts by INDEPENDENT third
  parties — NOT the company's own blog"), and injects the resolved own-domain as
  an explicit "do not target google.com" hint. Verified the rendered Google
  prompt now steers correctly.
  2. Log correlation — this was hard to trace because the pipeline's call_llm
  calls (planner/curator/summary) logged run_id=None/category_key=None; only
  IDENTITY/REPORT were tagged. I threaded run_id/category_key through so every
  LLM record is now correlated, per §7.

  Full suite: 132 backend + 29 frontend passing. The plan records the
  third-party-planner requirement.

  A couple of honest caveats:
  - There's a deeper related limitation still deferred
  (docs/FUTURE-IMPROVEMENTS.md): tavily_search hardcodes topic="news" for all
  categories, so blog/podcast/newsletter searches run through the news index.
  The prompt fix mitigates the own-channel problem, but per-category Tavily
  topic/params tuning would improve blog/podcast recall further — say the word
  and I'll implement it.
  - The runs already in your DB won't change retroactively; a fresh run (or
  Refresh) of Google will use the improved planner.
